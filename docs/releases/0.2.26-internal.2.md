# AgentBlazor 0.2.26-internal.2

> **Private/internal fork build.** This version is published only to the private local feed (`AGENTBLAZOR_LOCAL_FEED`, default `%USERPROFILE%\.agentblazor-feed`) and is **not** intended for public consumption.

## Fixed: Blazor Server renderer-thread deadlock in `AgentChatSurface`

### Root cause

`AgentChatSurface.OnInitialized()` called the **synchronous** `IAgentRegistry.GetAll()` on the Blazor Server renderer synchronization context. `RendererSynchronizationContext` is single-threaded, so a registry that hydrates over HTTP or a database blocks inside `GetAll()`, and the continuation it is waiting for is queued back onto the very context that is blocked. The thread can never pump it.

- Prerendering is enabled, so this ran on **both** the prerender and the interactive pass.
- The blocked thread holds the renderer, so this wedges the **whole server**, not one circuit.
- The consumer had no non-blocking option: `IAgentRegistry` offers no async seam, so a correct data-backed implementation had to write `service.ListAsync().GetAwaiter().GetResult()`.

### The fix

`AgentChatSurface` now reads agents through a new asynchronous seam instead of blocking the renderer thread.

| Point | Change |
|-------|--------|
| Injection | `IAgentRegistry` → `IAsyncAgentRegistry` (`src/AgentBlazor.Components/Chat/AgentChatSurface.razor`) |
| Lifecycle | `OnInitialized()` → `OnInitializedAsync()`, awaiting `GetAllAsync()` |
| Helpers | `ApplyAgentSelectionPolicy` / `ResolveRouteLockedAgentName` / `ResolvePrimaryRouteForAgent` renamed to `...Async` forms and awaited at every call site (including `OnParametersSetAsync` and the hand-off path) |

The accurate claim: **the renderer-thread deadlock is removed for registries that implement the async seam.** Sync-only registries are *relocated* off the renderer thread by a compatibility shim — see below.

## New: `IAsyncAgentRegistry` (additive)

`src/AgentBlazor.Core/Agents/IAsyncAgentRegistry.cs` — `IAsyncAgentRegistry : IAgentRegistry`. **`IAgentRegistry` itself is unchanged.** Three new members, each with a default interface method:

- `Task<IReadOnlyCollection<AgentRegistration>> GetAllAsync(CancellationToken = default)`
- `Task<bool> TryGetAsync(string name, Func<AgentRegistration, bool> onFound, CancellationToken = default)`
- `Task AddOrUpdateAsync(AgentRegistration registration, CancellationToken = default)`

### Design rationale: a callback instead of `out`

- C# forbids combining `out` with `async`, so an awaited value must be delivered through a continuation. `TryGetAsync` takes `Func<AgentRegistration, bool> onFound`.
- A `Task<AgentRegistration?>` return would conflate **"not found"** with **"found but null"**. The callback keeps `IAgentRegistry.TryGet`'s existing failure semantics exactly: an absent agent is `false`, never a `null` a caller could mistake for a populated result.
- The defaults are synchronous and exist for **source compatibility only**. An I/O-backed implementor that inherits a default instead of overriding it keeps the original block and merely relocates which thread blocks.

## New: `SyncAgentRegistryAsyncAdapter` (compatibility shim)

`src/AgentBlazor.Core/Agents/SyncAgentRegistryAsyncAdapter.cs` adapts a sync-only `IAgentRegistry` to the async seam by offloading each synchronous call to the thread pool via `Task.Run`.

**This is a compatibility shim, not a fix, and it is documented as such.** `Task.Run` does **not** eliminate the block — it relocates *which* thread blocks:

- the underlying call still occupies a thread-pool thread for its whole duration, and enough concurrent circuits can starve the pool;
- first render is still gated on the load completing, so startup stays as slow as the backing store;
- `CancellationToken` cannot interrupt work already running inside the synchronous call — `Task.Run(delegate, CancellationToken)` observes the token only *before* the delegate starts, never mid-flight.

What it buys: the renderer thread is never the thread that waits.

## DI: both interfaces resolve to the same instance

`AgentBlazorServiceCollectionExtensions` adds `TryAddSingleton<IAsyncAgentRegistry>` that resolves `IAgentRegistry` and returns it as `IAsyncAgentRegistry` when it already implements the interface, otherwise wraps it in `SyncAgentRegistryAsyncAdapter`.

- **Both interfaces always resolve to the SAME instance.** Two distinct registries would give the render path and the turn path divergent agent lists, so this is a correctness requirement, not an optimization.
- A consumer registration wins exactly as it does for `IAgentRegistry` (`TryAdd`, plus the documented replace path).

## `InMemoryAgentRegistry` overrides all three async members

| Member | Override and why |
|--------|------------------|
| `GetAllAsync` | `Task.FromResult` over the existing array-backed read — avoids a needless `Task` allocation on an already-materializing call |
| `TryGetAsync` | Preserves the O(1) keyed probe; the inherited default materializes everything and scans linearly, turning a dictionary lookup into O(n) on the per-turn resolution path |
| `AddOrUpdateAsync` | `Task.CompletedTask` — a `ConcurrentDictionary` write cannot block, so a thread-pool hop would add latency without removing any wait |

## Demo: `DatabaseBackedAgentRegistry` becomes genuinely async

- Implements `IAsyncAgentRegistry` with **real** async overrides: a `SemaphoreSlim(1,1)` load lock, `InitializeAsync`, and `RefreshCacheAsync` (EF Core `CreateDbContextAsync` / `ToListAsync` / `SaveChangesAsync`). The synchronous members are retained unchanged for non-render callers.
- `EnsureLoaded()` now **throws** when invoked before hydration instead of silently doing EF Core I/O on the renderer thread. Reaching it is a wiring bug (a missing or misordered startup hydrate), so it fails loudly.
- `Program.cs` registers the concrete type, aliases **both** `IAgentRegistry` and `IAsyncAgentRegistry` to that same instance, and hydrates at startup after migrations and seeding.
- **The alias line is load-bearing.** `AddAgentBlazor` cannot cover it: the demo had already replaced `IAgentRegistry`, so `AddAgentBlazor`'s own `IAsyncAgentRegistry` registration resolves the *shim* over the demo instance. Without the explicit alias, the render path would have kept resolving the thread-pool shim and the deadlock would have survived in the very app it was reported from.
- `AgentBuilder.razor`, `DemoSessionBrowserService` (`GetAvailableAgentsAsync`, `GetRouteForAgentAsync`, `BuildNewBaseSessionIdAsync`, `ResolveRouteFromRegistryAsync`), and `SessionBrowser.razor` were converted to the async members. A dead `IAgentRegistry` injection was removed from `SessionBrowser.razor`.

## Upgrade notes

- **No breaking changes.** `IAgentRegistry` is untouched and every new member has a default interface method, so existing custom registry implementations keep compiling and working unmodified. Existing sync-only registries keep working via the adapter.
- Implementing `IAsyncAgentRegistry` is **optional but recommended** for any registry that performs I/O — it is the only way to actually remove the block rather than relocate it.
- **If you implement it, register it against the SAME instance as `IAgentRegistry`.** The library's `TryAddSingleton` covers the common case, but if you replace `IAgentRegistry` yourself (as the Demo does) you must alias `IAsyncAgentRegistry` to that instance explicitly; otherwise the render path resolves the shim over your registry.
- Existing registries that inherit a default instead of overriding it do not regress, but they do not gain the fix either.
- **Version bump target:** this release is `0.2.26-internal.2`; the previous was `0.2.26-internal.1`.
